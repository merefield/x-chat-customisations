# x-chat-customisations

This plugin works alongside a fork of the core Discourse Chat plugin in
`/home/robert/code/chat`.

The table below is the current inventory of functional changes from base
Discourse Chat. The `Chat Fork` column shows whether the behavior depends on
changes in the forked chat plugin. The `x-chat-customisations` column shows
whether the behavior depends on code in this plugin. The `Relevant newer core
behavior` column captures the main base-chat change that now matters when
maintaining that customization. The `Review notes` column captures any current
audit follow-up for that row.

| Title | Description | Relevant newer core behavior | Review Notes | Chat Fork | x-chat-customisations |
| --- | --- | --- | --- | --- | --- |
| Explicit mention notification level | Adds a fourth channel notification level, `explicit_mention`. Users on this level still receive direct `@username` mentions, but opt out of broadcast-style mention notifications such as `@all` and `@here`. This feature depends on forked chat support for the extra enum value and client-side menu options, plus plugin-side notification handling. | Core still has only `never`, `mention`, and `always`, so the extra enum remains a fork responsibility. |  | Yes | Yes |
| Explicit mention settings and labels | Extends the channel notification settings UI to show the custom `explicit_mention` option and relabels the normal `mention` option with username-aware wording. The sidebar notification submenu now gets its rendered option list from plugin-owned logic, while the fork only exposes the overridable options seam. | Core moved notification controls into newer settings and sidebar components, so the customization now rides those extension points instead of the older route implementation. |  | Yes | Yes |
| Mention notification label | Sets the plugin-owned `mention` notification level label to `My Mentions + @all Posts` in the customized notification settings UI. | Core labels remain translatable client strings, but this plugin replaces the active `mention` option label while adding the explicit-mention option. | Tracking item #6. | No | Yes |

| Category channel posting modes | Adds a staff-only posting selector to category-channel settings with `Anyone can post`, `Only staff can post`, and `Only staff can post - replies allowed`. In this context "staff" means Discourse admins and moderators. The replies-allowed mode blocks non-staff from creating top-level channel messages while still allowing replies through chat threads. | Channel browse defaults to all channels | Changes the default channel browse route so `/chat/browse` opens the `All` tab instead of the `Open` tab, and orders the unfiltered all-channel browse list alphabetically. The plugin handles the full-page route default and backend ordering, while the fork routes the sidebar action through the default browse route and aligns the drawer default with `all`. | Covered by a system spec in `spec/system/channel_browse_spec.rb`. | Yes | Yes |
| Staff DM member limit bypass and zero-limit display | Staff get an infinite effective DM member limit, and the composer counter displays `Infinity` when `chat_max_direct_message_users = 0`. The plugin owns the effective limit override for group DM creation and add-members flows, keeps group rows enabled for staff, reroutes disabled group chatables into the new-group DM flow, and removes core's raw add-members username-count contract check so staff requests reach the existing staff-aware max-users policy. The fork still provides the `maxMembers` template seam used by the new-group DM composer. | Core backend DM policies exempt staff from the limit, but newer core also added a raw `usernames.length <= chat_max_direct_message_users` contract validation in `Chat::AddUsersToChannel`, which runs before the staff policy bypass. Core continues to treat `chat_max_direct_message_users = 0` as "no DM" for non-staff in the max-users policy; this plugin keeps the staff bypass without replacing the core policy globally. | User-group chatables still use core `can_chat` serialization and are enabled for staff in the UI override. | Yes | Yes |
| Staff category-channel member management | Restores staff ability to manage members from the category-channel members route by extending the UI capability checks and matching guardian behavior in the plugin. This keeps the staff-facing add-member controls available on category-backed channels after newer core permission changes. | Core tightened member-management checks around the members route and related capability flow, so the plugin now reintroduces the staff-specific allowance on top of those newer checks. |  | No | Yes |
| Channel creation default category | Prefills the create-channel modal with the category configured by `x_chat_customisations_channel_creation_default_category_id`, instead of making the user start from a blank category chooser every time. | Core still starts the modal without a custom default category. |  | No | Yes |
| Channel creation forces threading on | Defaults `threadingEnabled` to `true` in the create-channel modal and hides the threading toggle in that flow, so channels created through this UI path are threaded without presenting threading as a choice. | Core now handles unchecked booleans cleanly in the modal, so only the product choice to force threading remains custom. |  | No | Yes |
| Private channel bootstrap from dummy category | When a channel is created against the configured dummy private category, the plugin creates a new read-restricted category and a matching group named after the requested channel, rewrites the create request to use that new category, and makes the creator an owner of the new group. This turns one configured placeholder category into a private-channel creation mechanism. | Core channel creation still only creates channels against an existing category; it does not synthesize a category/group pair on demand. | Create path is now transactional; no migration required. | No | Yes |
| New category channels default `allow_channel_wide_mentions` to false | Changes the default for newly created category chat channels so `allow_channel_wide_mentions` starts disabled instead of inheriting base chat's default `true`. This affects whether `@all` and `@here` are enabled immediately after channel creation. | Core still defaults `allow_channel_wide_mentions` to `true`, so this remains a product-specific default override. |  | No | Yes |
| Private channel teardown cleanup | Extends channel deletion so channels created through the private-category bootstrap flow also remove their generated group, category-group join rows, category topics, and backing category during cleanup. This keeps the custom private-channel lifecycle symmetrical on create and delete. | Core delete cleanup removes chat-owned records only; it does not know about the extra category/group objects created by this plugin. | Remaining deferred review issue: cleanup is still keyed off mutable names rather than a stable identifier link. | No | Yes |
| Add-member sync for private/read-restricted channels | When users are added to a private category-backed chat, the plugin also adds them to the backing category group so category permissions stay aligned with chat membership. The override also creates new memberships at notification level `mention` instead of core chat's `always`. | Core `AddUsersToChannel` now allows the no-message 1:1 DM path, filters requested groups through visibility rules, and evaluates DM policies against the full participant set. The plugin now keeps those newer core behaviors while still adding private-category group sync and the custom notification default. |  | No | Yes |
| Username-based member removal API | Adds `DELETE /chat/api/channels/:channel_id/memberships/by-username/:username` for callers that identify members by username instead of user id. On private category-backed chats it also removes the user from the backing category group. This is intentionally additive rather than replacing the newer core user-id endpoint. | Core now has a user-id removal path in the members UI and API flow, so the username-based endpoint is kept as an additive compatibility surface. |  | No | Yes |
| Chat summary suppression for `@all` mentions | Alters chat-summary email eligibility so unread broadcast mentions created only by `Chat::AllMention` do not qualify a user for a summary email. Direct mentions and other supported unread cases still qualify. This currently lives in a mailer override that should track core mailer changes closely. | Core mailer now includes `to_address` in enqueued jobs and also includes unread watched-thread summaries, so the custom query has to be rebased on top of those newer paths. |  | No | Yes |
| Global disable for chat summary emails | Adds the site setting `x_chat_customisations_chat_summary_emails_enabled`. When disabled, queued `chat_summary` emails are skipped and recorded in `SkippedEmailLog` rather than delivered. | Core still enqueues chat summaries whenever eligibility matches; this plugin adds a second kill switch at mail-send time. |  | No | Yes |
| Enhanced email logging | Adds optional warn-level logging around `Jobs::UserEmail#send_user_email` and `#message_for_email` to help debug production email behavior. | Explicit mention notification filtering in the mention job | Extends the mention notification job so users whose channel membership is set to `explicit_mention` do not receive notifications for `@all`, `@here`, or other non-direct identifier types, while direct mentions still produce notifications. | Core mention-job behavior still notifies based on the standard channel notification levels, so `explicit_mention` remains a plugin-owned branch in the job flow. |  | No | Yes |
| Search exclusion semantics for membership lookups | Overrides chatable user search so `excluded_memberships_channel_id` excludes users who are already following a channel. This differs from current core behavior and should be treated as a deliberate search customization until it is narrowed or removed. | Core now applies the exclusion filter only when the acting user can preview the referenced channel; the plugin now keeps that new guard while preserving its `following = true` exclusion semantics. |  | No | Yes |
| Auto-join scheduler cadence | Re-registers `Jobs::Chat::AutoJoinUsers` to run every 10 minutes. This changes how quickly category chat channels with `auto_join_users` enabled pick up newly eligible users. | Core auto-join scheduling still runs on the default cadence, so this remains a plugin-side operational change. |  | No | Yes |
| Operator rake tasks for bulk seen-state changes | Adds `x_chat:make_seen` and `x_chat:make_unseen` rake tasks that bulk-update `last_seen_at`, either on one site or across all multisite databases. These are operational utilities, not end-user chat features, but they do change how the chat environment can be administered. | No equivalent core chat task exists; these are purely local operational helpers. |  | No | Yes |

## Notes

- Rows marked `Yes / Yes` need coordinated maintenance across both repositories.
- Rows marked `No / Yes` can usually be evolved entirely inside this plugin.
- The chat fork also contains a small number of extension seams, such as the
  overridable `notificationLevels` getter, that are not listed as standalone
  features here because they do not change user-visible behavior on their own.

## Chat Fork Dependencies

These forked chat files are current dependencies for `x-chat-customisations`.
They should be reviewed whenever the chat fork is rebased or the plugin is
changed.
